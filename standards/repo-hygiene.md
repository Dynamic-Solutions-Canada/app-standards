# Repo hygiene

The files and git habits every repo shares regardless of stack: licence, ignore and attribute files, branches, commits, dependency updates, and the policy files GitHub looks for. Repo names and owners are in [branding.md](branding.md); folder layout is in [repo-layout.md](repo-layout.md); formatter configuration is in [code-style.md](code-style.md).

Counts are out of the 15 in-scope repos unless a rule says otherwise. Server-side settings (visibility, branch protection) were not checked in the audit.

## Rules

### HYG-1: A licence file in every repo

- **Status:** Decided (D-008, D-006). Existing (most repos have a licence file and name the company, rechecked 2026-11-25; winui-app-kit is MIT; recount pending)
- **Applies to:** all
- **Reference:** `printstream/LICENSE` for the file name; `repilot/LICENSE` for the PolyForm text
- **Why:** A public repo with no licence grants nobody anything, and under D-004 every in-scope repo but printstream is public; phonelock and sonarbridge are public with none today.

Every repo has one licence file at the root (D-008):

| Repo | Licence | Copyright holder (D-006) |
| --- | --- | --- |
| Every app, and apps-promo | PolyForm Noncommercial 1.0.0 | Dynamic Solutions |
| game-is-up and store-sign-controller (personal projects) | PolyForm Noncommercial 1.0.0 | The individual owner (the repo owner's legal name) |
| devkit, winui-app-kit, web-app-kit, and windows-build-tools | MIT | Dynamic Solutions |
| printstream and printstream-home-assistant | printstream's own licence, with its `NOTICE` | As that licence states |

winui-app-kit carries PolyForm Noncommercial today, so it is relicensed to MIT; the seven existing licence files name the individual owner and are changed to the holder in the table.

The file is named `LICENSE`, with no extension, in every repo. Where the repo has a `package.json`, its `license` field agrees with the file: the SPDX id where one exists, otherwise `SEE LICENSE IN LICENSE`. A declared licence with no file is a defect (FIX-058). The copyright line names the holder in the table (see BRAND-3 in [branding.md](branding.md)). The README's `## License` section is README-5.

### HYG-2: No licence headers in source files

- **Status:** Decided (D-008). Existing (14 of 15 have none; little-launcher has headers in 41 of 178 files)
- **Applies to:** all
- **Reference:** any repo other than little-launcher
- **Why:** A half-applied header convention is copied inconsistently, and the root licence file already covers every file.

Source files carry no SPDX or copyright header. little-launcher's partial set is removed. Files copied from a third party keep whatever header their licence requires. This rule owns the point; STYLE-13 in [code-style.md](code-style.md) was merged into it.

### HYG-3: Third-party notices for shipped binaries

- **Status:** Decided (D-085). Proposed (most repos now comply, rechecked 2026-11-25; recount pending)
- **Applies to:** Windows, Web, Android (anything that ships a binary or image to users)
- **Reference:** `printstream/NOTICE`, `printstream/apps/api/THIRD-PARTY-NOTICES.txt`, generated by its `notices` script
- **Why:** Most open-source licences require attribution to travel with the binary, and a hand-kept list is wrong after the next dependency update.

A product that ships a binary includes a generated third-party notices file in the package, and the app's About page links to or shows it. The file is produced by a script from the lockfile or package list, not written by hand (D-085).

A `NOTICE` file describes the repo it sits in. A repo generated from another gets its own, not a copy of its parent's (FIX-024).

Android: the notices file is generated at build time per variant into the APK's assets (`third_party_notices.txt`), and the build fails when a module's POM chain names no licence or names one outside the app's allowed list. On AGP 8.13 or later the AboutLibraries Gradle plugin collects the licences (strict mode), with no AboutLibraries runtime library in the APK, and a small task renders its export to the text file. Reference: `persistent/apps/mobile/android-plugin/third-party-notices.gradle`. A repo still held at AGP 8.5.2 (D-095), where AboutLibraries registers no tasks, keeps the hand-written `generate<Variant>ThirdPartyNotices` task in sonarbridge's `android/app/build.gradle.kts` until its AGP upgrade. Proof of a working setup: the module list in the APK equals the variant's runtime classpath.

### HYG-4: Default branch and topic branches

- **Status:** Existing (15 of 15 use `main` as the default branch). Branch prefixes and clean-up are Decided (D-090)
- **Applies to:** all
- **Reference:** `repilot` (linear history on `main`); `printstream` for the staged variant
- **Why:** Workflow triggers, links, and agents all assume `main`; one repo's scan never runs because its trigger names another branch (FIX-028).

The default branch is `main` and history on it is linear. Topic branches are named `fix/<slug>` or `feature/<slug>`, in kebab-case, and are deleted once merged. Branches created by a tool keep that tool's prefix and are deleted the same way. A product that deploys in stages may work on `dev` and promote through `staging` to `main`, as printstream does; `main` is still the default.

A workflow trigger names only branches that exist in the repo; for every repo but a staged one, that is `main`.

### HYG-5: Commit subjects

- **Status:** Existing (11 of 15 follow the style throughout; printstream, devkit, printstream-home-assistant, and sonarbridge have older conventional-commit prefixes in their history). The fixed wording for bump and update commits is owned by REL-2 (D-097) and KIT-6
- **Applies to:** all
- **Reference:** `little-launcher` history
- **Why:** Subjects written as outcomes can be read as a change list and reused when drafting release notes.

A commit subject is an imperative sentence in sentence case, without a type prefix, that states the outcome a user or developer would notice ("Stop switching SFTP sync on for new installs"). Aim for under about 72 characters.

Two recurring commits use fixed wording so they can be found and filtered. Each is owned by the rule for its topic and only named here: the version bump is REL-2 in [releases.md](releases.md) (D-097), and a kit or submodule update is KIT-6 in [shared-kits.md](shared-kits.md).

When to commit, and the ban on attribution trailers, are in the user-level agent rules (kept outside this repo) and are not restated here. They apply to new commits; existing history is not rewritten.

### HYG-6: `.gitignore`

- **Status:** Decided (D-038). Existing (most repos now comply, rechecked 2026-11-25; recount pending)
- **Applies to:** all
- **Reference:** `persistent/.gitignore`; `tray-control-for-wsl/.gitignore` for the Windows tail
- **Why:** The ignore file is the last guard between a local secret or build output and a commit, and the gaps found so far are all in hand-copied files (FIX-002, FIX-003, FIX-031).

Every repo has a `.gitignore` in three parts, in this order. The shared block comes last so that no later line can un-ignore something it covers.

1. **Stack template:** the Visual Studio template plus the Windows tail (the packaging project's `bin/`, the build bridge's working folder) for Windows; `node_modules/` and `dist/` for Web; Gradle `build/` and `.gradle/` for Android.
2. **Project rules:** anything specific to the repo, each rule with a one-line comment saying why it exists.
3. **Shared block,** the same in every repo. For Windows repos on winui-app-kit it is the kit's `build/shared.gitignore`, and `external/winui-app-kit/scripts/check-gitignore .` in `validate` checks that the repo's `.gitignore` ends with it unchanged:

| Rule | Covers |
| --- | --- |
| `/.artifacts/` | Build output and evidence (LAYOUT-10 in [repo-layout.md](repo-layout.md)) |
| `/.windows-build/` | Local development signing material (Windows-building repos) |
| `.secrets/` | Local credentials (the name is D-038) |
| `.aws/` | Local cloud credentials |
| `.env`, `.env.*`, with `!.env*.example` | Environment files, keeping the examples |
| `tmp/`, `.backups/` | Scratch and local backups |
| `/.worktrees/` | Nested git worktrees, which live in `.worktrees/<name>/` (D-032) |
| `*.pfx`, `*.cer`, `*.der`, `*.keystore`, `*.jks` | Signing material, as a backstop |
| `local.properties` | Android SDK path |
| Editor and OS files | `.vs/`, `.idea/`, `.DS_Store`, `Thumbs.db` |

The Visual Studio template's `[Rr]elease/` rule also matches `.agents/skills/release/`, the standard `release` skill (AI-7, REL-8). A Windows repo that has the skill re-includes it in its project rules with `!/.agents/skills/release/`, and checks it with `git check-ignore`. Reference: winui-app-kit's `.gitignore`.

Directory rules end with a slash. A rule copied from another repo is checked for that repo's names before it is committed, and lines that match nothing are removed. What counts as a secret and where one may live are in [security.md](security.md); which agent folders are tracked is in [ai-docs.md](ai-docs.md).

This rule owns the ignore file; LAYOUT-14 in [repo-layout.md](repo-layout.md) was merged into it.

### HYG-7: `.gitattributes`

- **Status:** Proposed (most repos now comply, rechecked 2026-11-25; recount pending)
- **Applies to:** all
- **Reference:** `printstream/.gitattributes`
- **Why:** Without it, line endings depend on who checked the file out; one `.gitignore` is already checked out with CRLF where its twin is LF, and little-launcher has files with a byte-order mark (FIX-032).

Every repo has a `.gitattributes` that starts with `* text=auto eol=lf`. After that line come only the exceptions the repo needs, one per line:

- `eol=crlf` for `*.bat`, `*.cmd` and any other file type a Windows tool requires it for.
- `binary` for images, fonts, firmware, keystores, and other files git should not diff.
- `linguist-generated` for generated files that should collapse in diffs.

Text files are UTF-8 with no byte-order mark and are stored with LF endings. Scripts that run under bash or are executed directly are committed with the executable bit. Editor settings that match these are STYLE-1 in [code-style.md](code-style.md).

This rule owns encoding and line endings; STYLE-10 in [code-style.md](code-style.md) was merged into it.

### HYG-8: Dependabot

- **Status:** Decided (D-037, D-046). Existing (most repos now comply, rechecked 2026-11-25; recount pending)
- **Applies to:** all repos with dependencies or workflows
- **Reference:** `printstream/.github/dependabot.yml`
- **Why:** Pinned versions only stay safe if something proposes the updates, and grouping keeps that to one pull request a week.

`.github/dependabot.yml` has one entry per ecosystem in the repo (npm, NuGet, Gradle, pip, and `github-actions`), each on a weekly schedule with updates grouped. Every directory that holds a manifest or workflow source is listed, not only the root (FIX-052). Dependabot branches are merged or closed within the week; they are not left open. Every npm entry that installs devkit or web-app-kit ignores `@dynamic-solutions-canada/devkit` and `@dynamic-solutions-canada/web-app-kit`, with a comment: both are pinned to a release tag and bumped by hand following their release notes, and Dependabot misreads their git tags and proposes downgrades (devkit v0.20.3 to v0.17.1). Reference: `game-is-up/.github/dependabot.yml`. Not yet proven: whether Dependabot's NuGet updater follows the import from `Directory.Packages.props` into the kit's `build/WinUIAppKit.Packages.props`, or only updates versions written directly in the app's file. Until a Dependabot run shows it, the kit's own Dependabot updates the shared versions and apps take them by bumping the kit tag. Where the versions live in a folder with no project files (the kit's `build/`), Dependabot's re-create job for an open pull request runs only in that folder, finds no project, and closes the pull request as "no longer possible". Such an entry sets `rebase-strategy: disabled` with a comment saying why. Reference: `winui-app-kit/.github/dependabot.yml`.

This rule owns the Dependabot setup. Version pinning policy is PLAT-10 in [platform.md](platform.md), action pinning is CI-7 in [ci.md](ci.md), and how fast a security update must land is SEC-12 in [security.md](security.md). Choosing versions for new dependencies is covered by the user-level agent rules.

### HYG-9: Security policy and issue template in public repos

- **Status:** Decided (D-106, D-004). Proposed (most repos now comply, rechecked 2026-11-25; recount pending)
- **Applies to:** every public repo, which under D-004 is every in-scope repo except printstream (visibility is recorded per repo in BRAND-10 in [branding.md](branding.md))
- **Reference:** none yet
- **Why:** A public repo with no stated way to report a vulnerability gets it reported in a public issue, or not at all.

A public repo has `.github/SECURITY.md` saying how to report a vulnerability privately and which versions receive fixes, and one minimal issue template that asks for the app version, the OS version, and steps to reproduce. `SECURITY.md` goes under `.github/`, which GitHub recognises, so the root stays as short as DOCS-1 in [docs.md](docs.md) requires. The channel it names is GitHub's private vulnerability reporting, switched on for the repo, with the company contact (BRAND-9 in [branding.md](branding.md)) as the fallback.

Every repo's file is this template, which promises fixes for the latest published version only:

```markdown
# Security policy

## Reporting a vulnerability

Report it privately with the "Report a vulnerability" button on this repository's Security tab. Please do not open a public issue.

## Supported versions

Fixes are released for the latest published version.
```

The issue template is also where the support link in each app lands (BRAND-8 in [branding.md](branding.md), D-086), so it reminds the reporter what a log may contain before one is attached (see [logging.md](logging.md)). printstream is private and carries neither file; its public snapshot does.

This rule owns the file; how a reported problem is handled afterwards is SEC-15 in [security.md](security.md).

Pull request templates, `CONTRIBUTING`, `CODE_OF_CONDUCT`, `CODEOWNERS`, and `FUNDING` are not required; add one only when the repo starts taking outside contributions.

### HYG-10: Git hooks

- **Status:** Decided (D-030). Existing (9 app repos and web-app-kit run lefthook, rechecked 2026-11-25; devkit, winui-app-kit, apps-promo and printstream have no hooks)
- **Applies to:** all
- **Reference:** none yet in scope
- **Why:** A git hook applies to every tool and to people, where an agent tool's hook covers only that tool.

What must never be committed (generated files edited by hand, secrets, files over a size limit) is blocked by a git hook managed with lefthook, configured in one `lefthook.yml` at the root. Hooks are installed with `lefthook install`: the worktree `setup` in `paseo.json` runs it, and the developer guide tells people to run it once in a fresh clone. Repos without an npm dependency step rely on a user-level lefthook install rather than adding one. Husky is removed (FIX-042). Hooks stay fast: they check the staged files and do not run the test suite, which belongs to `validate` and CI (see [ci.md](ci.md)). Hooks that guide an agent during a session are covered by AI-11 in [ai-docs.md](ai-docs.md).

### HYG-11: Remotes and submodule URLs are current

- **Status:** Existing (every consumer uses the current submodule URL, rechecked 2026-11-25)
- **Applies to:** all
- **Reference:** `tray-control-for-wsl/.gitmodules`
- **Why:** A URL that works only through a redirect stops working the day the old name is reused or the redirect is dropped.

After a repo is renamed or moved, `.gitmodules` in every consumer, the local `origin` remote, and any script that names the repo are updated to the new URL in the same piece of work. Where submodules live is LAYOUT-7 in [repo-layout.md](repo-layout.md); their URLs use the owner recorded in [branding.md](branding.md). How submodules are pinned is in [shared-kits.md](shared-kits.md).

### HYG-12: Nothing built, stale, or machine-local is tracked

- **Status:** Decided (D-042, D-022). Existing (13 of 15 track no build output)
- **Applies to:** all
- **Reference:** `repilot` (no tracked binaries; releases carry the artifacts)
- **Why:** Tracked binaries grow the repo for ever, and leftover files are read by agents as if they were current.

That build outputs are published as release assets and not committed is owned by LAYOUT-13 in [repo-layout.md](repo-layout.md) (D-042), and the generated files a platform needs in the tree are ASSET-4 in [assets.md](assets.md); neither is restated here. This rule adds what is not build output. Unused project files are deleted, not kept "in case" (FIX-033), and configuration for a tool the repo does not run is either wired up or removed (FIX-056). Stale local copies of a repo are deleted: the dead `printstream-public` sibling clone goes once printstream's export scripts no longer default to it (D-022, FIX-051).
